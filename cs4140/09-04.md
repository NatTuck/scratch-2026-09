
# Core Workflow

## First: Issue

- Clear description describes what needs fixing (and why)
- Acceptance criteria: A manual testing procedure to confirm that the issue has
been fixed (typically: the problem is gone *and* the right behavior is happening
instead)

## Second: Do the work

- Issue gets assigned to someone (let's say Alice)
- Personal fork
- Locally clone
- Feature branch
- Work on feature branch locally
- First, create automated tests, which demonstrate the issue
- Run the tests, they should fail
- Write code to solve the problem
- Run tests, now they pass
- Manually confirm that acceptance critera are met
- Push branch to personal fork on github
- On github site, we can create a pull request.

## Third: Review the PR

- The PR is a new issue on Github
- It gets assigned to Bob (critically, Bob is not Alice)
- Bob confirms that the automated tests are passing, which means there
  are automated tests. (optimally in CI)
- Bob read the issue, pull the feature branch down locally, manually test
for acceptance critera
- Bob hits the Code Review button on Github
  - Read every line of modified code
  - Are the changes related to the issue?
  - Are the changes reasonable? (style, approach, efficiency, security, etc)
  - Problems: Comment in Github UI, ping Alice
  - Then Alice fixes any problems, repeat whole review process
- Once the PR is good, Bob hits "Squash and Merge"
- After the merge, Bob confirms the tests still pass. If not, revert and fix.
