## Application State

We can split the data in a computer program in to two parts:

- Static data (doesn't change when the program runs).
  - In botbash, this includes card art, card list, etc.
  - In Super Mario Brothers, the sprites, level layouts, etc.
- Dynamic data - or application state - does change at runtime.
  - In botbash, bot HP is a clear example of dynamic state.
  - In Super Mario Brothers, mario's position, height, coin count,
    enemy positions, etc.

State is annoying because it changes.

Two questions about state:

- How is it shaped? (what data type)
  - Partially, this is a data structures / efficacy question.
  - Mostly a design / systems analysis / "what are we doing?"
- Where does it live?
  - Very similar question: How long does it live?

Where could we put it (assume a multiplayer game).

Two kinds of computer: client, server

On each kind of computer, we get to pick:

- RAM, for short-lived / transient state
  - If it doesn't need to last past one game session, then maybe just RAM?
  - If we need to read or write the data in less than a millisecond, it
  definitely needs to be in RAM.
- Disk, for long-lived / persistent state
  - If it needs to survives a reboot, it definitely goes on disk.

Which place does it go?

- client
  - If the player needs to see it, it must be on the client.
  - If the data comes from a player, it must be on the client.
  - If the data comes from the player and then must lead to rendering
    in less than the network latency, the whole thing must happen
    on the client.
- server
  - if two players need to see it, it must be on the server.
  - If the server wants to enforce rules about data, the data
  must be on the server.

Having things in two places is a problem. Which copy is correct?

- If there's a copy on the server, we *want* to declare that the
server has the correct copy and is the "single source of truth".
