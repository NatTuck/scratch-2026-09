
## Programming Languages

Why pick a programming language?

**Familarity**

- Which is usually why people might claim it's "easier".
- This is the cause and effect of popularity.

(Similarly)

- Your boss is familiar with this language, so they pick it.

**Concrete Differences**

- Framework / Library support.
  - If you want to use Unity, you're done with choices about language.
- Some languages provide library functionality / simplicity.
  - Popularity can lead to better library / framework support.
- Sometimes you're targeting a specific platform, and a specific
language might give direct access (e.g. C for Unix / Linux, JavaScript
for browser).
- Performance:
  - Raw execution speed
- Language runtime functionality / structure
  - Some languages are better/worse at concurrency
  - Cross-platform support
- Correctness features
  - Type system
  - Platform invariants (i.e. functional style)

## But what if we weren't writing the code?

- Let's assume we have an LLM both write and review the code.

We want the LLM to support the language: It's been trained on all the major
ones, but inventing a new one might not be optimal.

Familiarity doesn't matter as much, but all the concrete differences
matter.

Especially interesting languages:

- Scala, the language with the most complete type system on the JVM.
- Rust
  - Fast, because compiles to machine code
  - Good concurrency support, because that's designed in
  - Strong types
  - Safe memory handling
- C
  - This is the "real" low level language that the operating system interfaces
  are built for.
  - Need to put in static analysis, but we can do that too.
- TypeScript
  - JavaScript is required in browser?
  - Nah, we can have strong types too.
- Elixir / Erlang
  - Have a very specific concurrency / reliability story.
  - Re-implementing the Erlang VM would be non-trivial, and if you want
  the functionality that's the other choice.
- Go
  - The compromise between Rust and Elixir
  - Good raw performance (not the best)
  - Good concurrency story (not the best)
  - Always produces static binaries, so compile on one machine
  and run on anther

## Why Elixir?

I tricked Lysander into merging the Elixir Backend PR.

Elixir is a lanugage that runs on the Erlang VM (much like how
Scala or Groovy runs on the JVM).

Why Erlang?

- Built for telephone switches.
- Telephone networks work, even on Tuesdays
  - The uptime guarantee is "five 9's", or 99.999% of the time
  the network is up - that's 5 minutes down per year.
  - No downtime for patches / scheduled maintenance.
  - A phone call can drop, but it can't break anything else.
- What does software need to look like to make that work?
  - Hardware redundancy is required. If a piece of hardware
  fails, we need to swap to the backup.
  - But hardware redundancy means we have a distributed system.
  - All the problems that everyone else put off until 2005,
  Erickson had to solve in 1987.

Why Elixir over Erlang?

- Erlang uses periods to end sentences.
- You can't call user defined functions in if expression
conditions.
- Elixir is a nice, modern language with lots of
nice features, frameworks, and libraries.

## No really, why Elixir / Erlang specifically?

Elixir / Erlang is based on many concurrent processes.

Processes are like threads, but without shared memory. So you can't have a
simple data race. Communication is by message passing between processes.

The Erlang standard library is called OTP, or the Open Telecom Platform.

Key ideas:

- Supervior tree
  - Every process in a program lives in a supervision tree.
  - The root of the tree supervises its children, they supervise theirs,
  etc.
  - When a process crashes, its parent is notified and can decide to restart
  it, log the error, crash itself, or whatever.
  - "Let it crash"
- GenServer
  - A way to manage medium-livetime state.
  - When someone access their farm in grange, they'll probably talk to
  their own process which holds their server state.

Really neat thing we probably won't be using:

- Live code loading for online upgrades.
