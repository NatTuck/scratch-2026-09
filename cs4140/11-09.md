
## Passwords

Last time we saw that a 4 digit password was enough if we could stop attempts
after a dozen or so.

And we concluded that storing passwords in plain text is a bad idea.

Clever idea: Hash passwords with a cryptographic hash function.

If we use sha256(password), and store that in our DB, then nobody who gets
the database can ever get the password.

Common passwords:

- birthday
- favorite pokemon
- favorite pokemon with a number after it
- abc123
- password
- password1
- Password1!
- plymouthstateisawful

We can build a "password dictionary", of all the common words.

For each word in the dictionary, we can extend it:

- password
- password1
- password1!
- password2

Cryptographic hash algorithms are fast, by design. That's bad for password
hashes. So we can have intentionally slow algorithms: bcrypt, argon2, scrypt

We can save some compute by pre-calculating the hashes. This is called rainbow
tables.

Fix for that is to salt our passwords. For each user's password we genrate a
random 32-bit integer k and hash (password + k), and store k.

**Password Guidelines**

- Have a bunch of different kinds of character.
- Periodic password resets.
- Minimum length.

Current recommendations are just:

- Require minimum length (~12)
- Maybe reject common words
